# Модель: подробное описание работы

## 1. Назначение

Этот документ описывает текущую ML-систему проекта для задач по объявлениям Avito в домене ремонта. Цель пайплайна:

1. Определить, к каким микрокатегориям относится исходное объявление.
2. Понять, нужно ли разбивать объявление на несколько отдельных draft'ов.
3. Сгенерировать draft-тексты для найденных микрокатегорий.

Система построена как многоступенчатый pipeline, а не как одна монолитная модель. Это сделано намеренно: часть качества достигается retrieval-этапом, часть — transformer reranking'ом, часть — пороговой и ранжирующей логикой на этапе inference.

## 2. Общая схема пайплайна

Текущий путь данных выглядит так:

1. Загружаются микрокатегории из `rnc_mic_key_phrases.csv`.
2. Загружается датасет объявлений из CSV или JSONL.
3. Датасет делится на `train`, `val`, `test` по полю `split`.
4. Для каждого объявления строится набор candidate'ов через TF-IDF retrieval.
5. Текст объявления кодируется transformer'ом.
6. Для каждого candidate'а считается score классификатора.
7. Отдельная бинарная голова оценивает `shouldSplit`.
8. На основании score, threshold'ов и reranking-правил формируется итоговый список draft'ов.
9. Для каждого draft'а генерируется короткий текст.

Итоговый ответ системы соответствует схеме:

- `detectedMcIds`
- `shouldSplit`
- `drafts`

## 3. Структура данных

### 3.1. Микрокатегории

Микрокатегории загружаются из CSV-файла с колонками:

- `mcId`
- `mcTitle`
- `keyPhrases`

Для каждой микрокатегории хранится:

- идентификатор,
- название,
- список ключевых фраз.

Ключевые фразы используются как основа retrieval-модели.

### 3.2. Размеченные объявления

Каждая строка датасета содержит:

- `itemId`
- `sourceMcId`
- `sourceMcTitle`
- `description`
- `targetDetectedMcIds`
- `targetSplitMcIds`
- `shouldSplit`
- `caseType`
- `split`

Важные поля для обучения и оценки:

- `description` — входной текст.
- `sourceMcId` — исходная категория объявления.
- `targetSplitMcIds` — список микрокатегорий, которые должны попасть в split draft'ы.
- `shouldSplit` — бинарный флаг необходимости разбиения.
- `split` — принадлежность к train/val/test.

## 4. Формат задачи

Задача здесь не сводится к простой многоклассовой классификации. Это гибридный pipeline:

1. Retrieval находит широкий пул релевантных микрокатегорий.
2. Transformer reranks кандидатов.
3. Дополнительные threshold'ы, margin'ы и ограничения на число draft'ов снижают шум.

Такой подход полезен, потому что:

- микрокатегорий мало, но они сильно пересекаются по смыслу,
- текст объявления часто шумный и короткий,
- нужен не только класс, но и решение о сплите,
- итоговая метрика чувствительна к лишним draft'ам.

## 5. Кодовая архитектура

Основная логика находится в `model/model.py`, запуск обучения — в `model/run.py`.

### 5.1. Основные dataclass'ы

В модели используются следующие структуры:

- `MicroCategory`
- `Item`
- `LabeledItem`
- `Draft`
- `PredictionResult`
- `PipelineSettings`
- `TrainingSettings`

Они разделяют:

- описание входных данных,
- параметры пайплайна,
- параметры тренировки,
- формат итогового предсказания.

## 6. Retrieval-этап

### 6.1. Зачем нужен retrieval

Перед transformer-ом стоит retrieval-слой, который отбирает candidate'ов из всех микрокатегорий. Это снижает шум и делает дальнейшее ранжирование более управляемым.

Без retrieval модель либо:

- слишком часто выбирает лишние категории,
- либо вынуждена ранжировать все категории сразу без предварительного ограничения.

### 6.2. Как работает retriever

Retrieval реализован через `TfidfMicroCategoryRetriever`.

Он использует:

- word TF-IDF с n-gram диапазоном `(2, 3)`
- char TF-IDF с n-gram диапазоном `(2, 4)`
- blended score между word и char частями

Текущая комбинация весов:

- `word_weight = 0.85`
- `char_weight = 0.15`

Это было выбрано после экспериментов: char n-grams сильно поднимают recall, но без снижения веса начинают добавлять слишком много ложных candidate'ов.

### 6.3. Документ микрокатегории

Для каждой микрокатегории строится текстовый документ из `keyPhrases`.

Особенность: key phrases дублируются внутри документа, чтобы усилить влияние категориально важных терминов.

Это помогает TF-IDF лучше различать похожие категории.

### 6.4. Что возвращает retrieval

Retrieval-этап возвращает:

- список `detected_mc_ids`
- словарь TF-IDF score'ов по category id

Эти значения затем используются как часть финального scoring'а.

## 7. Transformer-часть

### 7.1. Назначение

Transformer нужен для более глубокого семантического понимания текста объявления и для reranking candidate'ов.

### 7.2. Архитектура

Используется `TransformerSoftmaxSplitModel`.

Компоненты:

- `AutoTokenizer`
- `AutoModel`
- `projection` layer
- `mc_embeddings`
- `split_head`
- `temperature`

### 7.3. Encoding текста

Текст объявления:

1. токенизируется,
2. подается в transformer,
3. pooled representation строится через masked average pooling,
4. результат проходит через linear projection и dropout.

Это дает компактный embedding текста.

### 7.4. Scoring по категориям

Для candidate'ов используются trainable embeddings микрокатегорий.

Скоры считаются через dot product:

- embedding текста
- embedding candidate'ов

Потом logits нормируются через temperature.

Это поведение фактически похоже на learned reranker over candidate set.

### 7.5. Отдельная голова `shouldSplit`

Есть отдельный бинарный head:

- `split_head = nn.Linear(hidden_dim, 1)`

Он обучается отдельно от category head и предсказывает `shouldSplit`.

Это важное улучшение, потому что бинарное решение и выбор категорий — разные подзадачи.

## 8. Обучение

### 8.1. Поток обучения

Обучение идет батчами, но loss считается по каждому примеру внутри батча.

Для каждого примера:

1. строится list candidate'ов,
2. считается embedding текста,
3. считаются logits по candidate'ам,
4. строится target distribution,
5. считается KL divergence loss,
6. отдельно считается binary cross-entropy для `shouldSplit`,
7. суммарный loss backpropagates.

### 8.2. Target distribution

Если среди candidate'ов есть целевые категории, они получают нормализованные веса.

Если target'ов нет в candidate set, fallback'ом используется source category либо равномерное распределение.

Это удерживает обучение стабильным и позволяет использовать soft targets вместо жесткого one-hot.

### 8.3. Loss

Общий loss состоит из двух частей:

- KL divergence для candidate classification
- BCEWithLogitsLoss для `shouldSplit`

Итог:

`total_loss = category_loss + split_loss_weight * split_loss`

### 8.4. Early stopping

Есть early stopping по validation F1.

Логика:

- после каждой эпохи считается качество на val,
- подбирается threshold,
- если F1 перестает улучшаться, счетчик patience уменьшается,
- при исчерпании patience обучение останавливается,
- лучший checkpoint восстанавливается.

## 9. Thresholding и calibration

### 9.1. Global probability threshold

Сначала подбирается общий `prob_threshold`.

Он используется для отбора draft'ов из score map.

### 9.2. Split threshold

Отдельно подбирается `split_threshold` для бинарного решения `shouldSplit`.

Это дает независимую калибровку решения о том, надо ли разбивать объявление.

### 9.3. Per-class thresholds

Потом подбираются индивидуальные пороги по каждой микрокатегории.

Это нужно потому, что:

- одни классы модель предсказывает слишком уверенно,
- другие, наоборот, требуют более мягкого или более жесткого порога,
- единый threshold не оптимален для всех.

### 9.4. Что оптимизируется

Подбор параметров может идти по:

- `f1`
- `precision`
- `recall`

Можно задать и минимум по recall, если нужно удержать покрытие.

## 10. Reranking и post-filtering

Это одна из ключевых частей текущего решения.

### 10.1. Почему это нужно

Один только threshold часто плохо работает:

- слишком много ложных draft'ов при низком пороге,
- слишком много пропусков при высоком пороге.

Чтобы снизить эту проблему, используется reranking logic.

### 10.2. Что сейчас делает reranker

Для каждого candidate'а считаются:

- transformer score,
- TF-IDF score.

Потом эти два сигнала смешиваются:

`blended_score = alpha * model_score + (1 - alpha) * tfidf_score`

Текущий лучший режим на валидации показал, что `alpha = 0.9` работает лучше остальных конфигураций.

### 10.3. Margin filtering

После сортировки по blended score применяется margin-правило:

- оставляем candidate'ы, которые достаточно близки к top score,
- слишком слабые кандидатуры отбрасываются.

### 10.4. Relative ratio filtering

Дополнительно может использоваться rule вида:

`score >= top_score * relative_ratio`

Это помогает оставлять только заметно сильные категории.

### 10.5. Ограничение числа предсказаний

Есть `max_drafts`.

Если он больше нуля, список draft'ов обрезается до этого количества.

Это может повысить precision, но не всегда лучшее решение. В некоторых экспериментах лучше работал режим без жесткого cap.

## 11. Предсказание

### 11.1. Последовательность

При inference происходит следующее:

1. retrieval отбирает candidate'ов,
2. transformer считает score по каждому candidate'у,
3. scores смешиваются с TF-IDF,
4. применяется per-class threshold,
5. применяется margin / ratio / max_drafts,
6. отдельно предсказывается `shouldSplit`,
7. draft'ы создаются только если `shouldSplit = True`,
8. для каждого draft'а генерируется текст.

### 11.2. Генерация draft текста

Сейчас draft text строится шаблонно:

- добавляется название микрокатегории,
- короткая выжимка из исходного объявления,
- короткая фраза о качестве исполнения.

Это не LLM-генерация, а безопасный deterministic шаблон.

## 12. Метрики

### 12.1. Что считается

Валидационные метрики строятся по сравнению:

- predicted draft `mcId`
- gold `targetSplitMcIds`

Рассчитываются:

- `precision_micro`
- `recall_micro`
- `f1_micro`
- `should_split_accuracy`

### 12.2. Что не влияет напрямую

На итоговый split-F1 не влияют напрямую:

- `detectedMcIds`
- retrieval scores как таковые
- source category id

Но они косвенно влияют через то, какие categories дойдут до финального отбора.

## 13. Эволюция экспериментов

### 13.1. Что пробовали

Были протестированы:

- word-only TF-IDF retrieval,
- char n-grams,
- смесь word/char retrieval,
- более сильный encoder,
- per-class thresholds,
- reranking controls,
- ограничения на число draft'ов,
- аугментированный train dataset,
- clean hard negatives dataset.

### 13.2. Что оказалось полезным

Самые полезные изменения:

- char n-grams с умеренным весом,
- per-class thresholds,
- reranking score blending,
- margin-based отбор,
- early stopping,
- подбор thresholds на val.

### 13.3. Что оказалось хуже

Аугментированный dataset без дополнительной фильтрации снизил качество по сравнению с более аккуратной схемой обучения.

То есть простое расширение объема данных не гарантирует рост метрик.

## 14. Текущие лучшие результаты

На одном из последних прогонов был достигнут сильный результат:

- `precision_micro` около `0.8687`
- `recall_micro` около `0.8605`
- `f1_micro` около `0.8646`
- `should_split_accuracy = 1.0`

Это стало возможным не за счет одного большого encoder'а, а за счет комбинации:

- сильного base encoder'а,
- retrieval с char n-grams,
- per-class calibration,
- reranking score blend,
- margin/ratio logic.

## 15. Почему это работает

Ключевая идея текущего решения:

- retrieval отвечает за recall,
- reranking отвечает за precision,
- thresholds и controls отвечают за баланс,
- отдельная `shouldSplit` голова отделяет бинарную логику от multi-class логики.

Такой декомпозированный подход лучше, чем одна большая модель, которая одновременно пытается решать все аспекты задачи без явного контроля на каждом этапе.

## 16. Ограничения и риски

### 16.1. Ограничения

- Метрика чувствительна к шумным labels.
- Пороговые правила могут быть подогнаны под val.
- Некоторые классы естественно сложнее остальных.
- Высокий precision может быть достигнут ценой recall и наоборот.

### 16.2. Риски переобучения

Если слишком долго тюнить threshold'ы и controls на одном val, можно получить хорошую валидацию и ухудшение на test.

Поэтому важны:

- честный holdout,
- аккуратная аугментация,
- контроль leakage.

## 17. Практическое использование

Обычный запуск обучения выполняется из `model/run.py`.

Пайплайн:

1. загружает данные,
2. строит pipeline,
3. обучает модель,
4. калибрует thresholds,
5. тюнит reranking controls,
6. печатает report,
7. показывает sample prediction.

## 18. Что имеет смысл улучшать дальше

Если идти дальше, наиболее полезные направления:

1. Hard negatives из реальных ошибок.
2. Pairwise / ranking loss поверх candidate'ов.
3. Дополнительный reranker на top-k.
4. Чистка шумных label'ов.
5. LLM как teacher для генерации качественных hard examples или paraphrases.

## 19. Итог

Текущая модель — это не просто classifier, а многоступенчатый retrieval + reranking pipeline с калибровкой порогов и правилами постобработки.

Важнейшие выводы из всех экспериментов:

- один encoder сам по себе проблему не решает,
- retrieval и post-filtering критичны,
- per-class calibration полезнее общего порога,
- reranking с комбинацией model score и TF-IDF score дает сильный прирост,
- жесткий cap на число draft'ов не всегда лучший выбор,
- на следующем этапе стоит идти в hard negatives и ranking-oriented training.
